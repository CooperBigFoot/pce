# Grill Ticket

Resolve the supplied Effort number in the current verified repository, or use the repository identified by its GitHub URL. Ask only for missing or ambiguous identity. Read the ticket, comments, relevant Program context, repository evidence, and any linked vision. Confirm repository identity and permissions before changing anything. If another user is assigned, stop and resolve ownership rather than taking over. An explicit draft-only request permits no assignment or other GitHub mutation.

Load the canonical [grill-me](../grill-me/SKILL.md) conversation and apply it in depth to this Effort. Issue content is input, not proof that the user endorsed an agent's assumptions. Preserve settled decisions, investigate conflicting or newer evidence, and discuss genuine user choices rather than inventing a second interview mechanism. On resume, reconstruct understanding and explore only changed, contradictory, or unresolved territory. Real blockers can constrain delivery without preventing discovery.

Keep material findings and decisions in concise issue comments when publication is authorized, linking existing context rather than repeating it. Do not require a separate context document or comments about placeholder status.

After the interview's confirmed summary, this explicitly requested workflow authorizes creating or revising a normal vision through [to-vision](../to-vision/SKILL.md), including its authoring checks. Reuse an existing vision path when revising. Include an ordinary link to the associated Effort so a later session can recover the context; no Program metadata or ticket-specific template is required. Do not silently replace settled content or guess between conflicting vision links.

For draft-only output, stop at the local draft without publication or an implementation handoff. Otherwise follow the shared [publication procedure](../to-vision/publication.md) once and consume its verified result. It owns review, merge, issue linkage, and target-copy verification. Do not duplicate those actions here.

Publishing a vision is not delivery: leave the Effort open. Report the vision path, publication PR and Effort URL, or the precise partial failure. Only a verified publication permits the handoff `implement-vision <Effort number or URL>`. Do not start implementation.
