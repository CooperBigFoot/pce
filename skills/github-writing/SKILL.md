# GitHub Writing

Apply these rules when authoring GitHub issues, PR bodies, and publication, delivery, or landing summaries. Loading this guidance does not invoke publication or another workflow.

Start with a short, plain explanation of the problem or change and why it matters. Use concrete actions and examples, not dense technical noun phrases. Keep technical precision, but make the point understandable without implementation knowledge or opening details. Simple bugs, reminders, and placeholders need only enough information to take up the work; leave deeper discovery to the grill. Preserve the established Program and Effort contracts.

Use structure only when it helps this explanation. No heading set, diagram, glossary, evidence section, or risk label is mandatory. Visuals and before/after comparisons are optional. Put necessary technical detail in optional, clearly named HTML `<details>` blocks that GitHub renders collapsed, organized by use such as reproduction, investigation, or verification. Do not create an appendix merely to fill a template. Link existing durable records instead of duplicating them when useful.

Keep current blockers, breaking changes, and material limitations visible in the main explanation. Describe the current state, not a diary of intermediate tests and reviews. Preserve required verification evidence, reproduction information, and durable recovery records while simplifying their presentation. Keep private material private. Preserve canonical links, markers, provenance, dependencies, authoritative delivery records, and no-auto-close safeguards; readable prose must not weaken machine-checkable contracts.
