# GitHub Writing

Write the smallest useful context for the next action. GitHub records support to-do lists, later discovery, coordination, review, and audit; they are not always requests for human attention. Loading this guidance starts no workflow and grants no publication authority.

Use precise titles and proportionate bodies. A one-line reminder is valid. No headings, action-item section, evidence appendix, audience labels, or human-facing narrative are mandatory. Link existing context instead of repeating it; link or collapse substantial details when useful, not by default.

Make records easy to scan. Explain the purpose in short plain prose, then use bullets for distinct changes, decisions, or actual next actions. A PR with several changes lists them so each is easy to find instead of burying them in a paragraph. A discussion record separates settled understanding from what remains open. Headings and collapsed details are optional aids; a short record can stay short, and no mandatory structure does not mean avoiding useful structure.

A bug report usually needs the problem, reproduction steps, and expected behavior. Include the version, revision, or conditions when relevant. Distinguish observed facts from hypotheses. The fixing agent must verify the report. Do not invent reproduction evidence from source inspection or an advisory. Suggested fixes are optional brief ideas, not implementation code.

Preserve evidence that cannot readily be recreated, such as intermittent failures or disappearing responses. Keep private data private. Keep blockers, material limitations, safety constraints, unverified results, unfinished work, and necessary human decisions visible. Concision must not hide them.

When human attention is needed, state the actual request and its purpose. For example: “Please try selecting stations and copying a Python request. Does the flow make sense without explanation? I’m looking for usability feedback, not a code review.” Do not manufacture a request when none exists.

PRs explain the change and useful verification context, not the investigation diary; link detailed evidence rather than narrating the investigation. Visions, issues, and PR evidence can carry detail once. Use neutral issue references when publication or partial implementation must leave the issue open.
