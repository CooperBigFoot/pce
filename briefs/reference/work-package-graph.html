The Work-Package Graph

PCE stops being an orchestrator. It becomes the layer that says what the work is, what would prove it, and whether the built thing survives attack. It no longer decides who runs what, where, or how.

Three owners

Who decides what

PCE

The Program and its tickets. The vision and its executable criteria. The work-package graph. The repository contract. The event log. The cost meter. The gates.

herdr

Worktrees, spawning, liveness, and the pane state a human can see at a glance.

prime-agent

How a work package actually gets built. Full autonomy inside the node.

Tool-specific knowledge may leak freely into the workflow, the verbs, and the skill — iteration is cheap and attachment is the real cost. It may not leak into the event log or the acceptance criteria, because those are records that get replayed by future code and must outlive the current harness.

Where the human touches it

Two recognition moments · nothing technical, ever

  1. The vision. Charted with an LLM as a thinking partner, then grilled one ticket at a time. This is the part that already works, and it does not change.
  2. The shape of the finished world. One look at the graph below before execution — not to review it technically, but to flinch at a world that isn't the one intended. The most expensive failure on record (eleven providers' pipelines deleted, correct against the vision, approved by two critics) was caught only when a human saw “~6,000 lines deleted” in passing.

After that, three things and only three things may interrupt:

  • spending money
  • an act that cannot be undone, or that leaves the machine
  • the work having drifted from the world that was asked for

Anything else that stops the system is a defect in PCE, to be reported — never a decision handed to the human. A question the human cannot answer from taste is a defect in the question.

Where the graph comes from

The only planning that survives · once per plan version

One dispatched pass reads the vision, its ratified criteria, and the source at a named ref, and emits the graph. Each node carries an id, the repositories it touches, its acceptance criteria as executable commands, and for each dependency the code fact that makes this node unbuildable until its predecessor merges.

Recovery’s third rung mints a new plan version rather than mutating the graph, so authoring re-enters for the affected region. The human is notified only when the new version changes which of the vision’s criteria are covered — checkable, and exactly the “drifted from what you asked for” condition. A re-cut that moves only internal boundaries re-renders without interrupting.

What a node does

Completion and the recovery ladder

A node is not complete when the builder stops. It completes when its acceptance criteria execute and pass, and a gate holding different capabilities tries to break the built artifact and fails. Building and attacking never share permissions.

The graph

Eight work packages · opening ready set of three

A work package is the largest unit whose acceptance criteria can be written as executable commands. Not a size — a property. Too large and adversarial review degrades into reading a diff, which catches nothing. Too small and it is a step again.

What survives, what dies

The seam is durability, not sentiment

Survives

outlives the harness

  • The Program layer: map, tickets, Fog, the grill, CONTEXT.md, ADRs
  • The vision and its ratified, executable acceptance criteria
  • The repository contract, measured at base on the default branch
  • The append-only event log as the only durable state
  • The graph, its justified edges, and the computed ready set
  • Adversarial gates against the built artifact
  • Worktree isolation, two-tier merge, human-only tag and release

Dies

roughly a third of every run

  • steps.json and the entire step tier
  • Step plan documents and their critics — 63 of 197 dispatches, measured
  • The blind cold executor and the serialized universe a plan had to carry for it
  • Route anchors, the placeholder vocabulary, the exactly-three --env rule — ~100 of 542 lines of doctrine
  • pce dispatch spawn and liveness, including the pid-and-start-identity sidecar
  • Runtime delta stubs as a way to change the graph

What would prove it

The only honest acceptance test

Take one of the six live repositories, convert its in-flight vision to the new format, resume it from where it actually stands — and it runs unattended and lands.

Stronger than a greenfield vision, because it proves the migration and the mechanism at the same time, on work that is already half-finished and already stuck. The remaining five convert the same way once it holds.

Supporting criteria, all executable: no node can become permanently undispatchable; an exhausted node parks, stays resumable, and the run continues around it; and the three human conditions are the only paths that stop and notify.

Backwards compatibility is explicitly not required. Old event logs need not replay under the new code. What is required instead is a written migration procedure — for each repository, how to express its current position in the new format and continue from there. That is WP9’s real deliverable, and it is worth more than a compatibility layer nobody will need twice.

Two loose threads

Named rather than quietly assumed

The human surface is an artifact, everywhere. Not just the graph — run state, deviation notices, and the finished result too. An artifact is readable by someone who does not know the workflow’s vocabulary, which is the actual requirement behind the 3am problem, where every surface reaching a human was written in role names, verdict fields and file paths.

Multi-repository work is under-determined. A node names the repositories it touches and herdr creates one worktree per repository per node; the repository contract is already per repository. What is not settled is whether a cross-repo node needs a rule beyond running the consumer’s own stated test command. The Program map records this as open, noting the evidence needs a deliberately multi-repository run — two consecutive visions touched cross-repo behaviour and neither produced a single observation, because both were single-repo. Treat it as unresolved, not designed.

Deliberately out of scope

Named so it isn't answered by accident

The knowledge interface. There are seven overlapping knowledge stores — CONTEXT.md, ADRs, both halves of the repository contract, event-log key findings, the Program map, and SKILL.md. Unifying them, and deciding what falsifies each kind, is open design work. It is excluded here so that a machine does not answer it plausibly and unverifiably.

The eight legacy prose visions that pce status cannot parse. Pre-existing, measured identically on the current binary, unchanged by this design.

Sequencing

Order matters exactly once

The repair branch raises the snapshot schema to v2, and strict v1 consumers reject v2. Merge, rebuild, then restart all six live sessions — in that order. Do not merge while runs are in flight: mid-run schema churn has already discarded two correct reviews once.
