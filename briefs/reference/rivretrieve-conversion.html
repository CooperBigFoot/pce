Step one: partition the criteria

Packages come from what must exist, not from the scope list

Step two: the edges come in three kinds

Only two of them bind the scheduler

Buildability

B does not compile or run until A has merged. Must name the code fact. Forced.

Safety

B does something irreversible that A must exist to protect. Must name the act. Forced.

Risk-ordering

B after A so a defect is found cheaply. A choice, not a constraint. Can be overridden.

The critical path, and the one decision on it

Where the time actually goes

The longest chain is RR1 → RR2 → RR3 → RR5 → RR7. Everything else has slack.

Poland is not on it. That inverts the intuition. RR4 reads as the risky long pole — it is the falsifier for the whole layout — but it only has to finish before RR7. Meanwhile the bulk surface, which reads like a tidy finishing task, sits directly on the spine.

The contract split was tried and rejected

The standard cut — when many nodes wait on one producer, extract the interface so the implementation runs beside its consumers — does not apply here. RR6 genuinely needs only the query-metadata shape, but it already sits in the first wave. RR2 needs the reader's behaviour: its read-back compares the completed store field for field through the same reader a user query uses, and against a stub that comparison is vacuous.

Extracting a contract node adds a serial step at the front and lengthens the critical path from five nodes to six. The transformation is real; it just does not fit this graph, whose bottleneck is a chain of behaviour dependencies no interface extraction touches. Recorded as a negative result so it is not re-proposed.

The split that would help is at RR3, not RR1

RR5's dependency on RR3 is over-strong. Read its criterion literally: “Call fetch for a ca_eccc station on a machine with no local store”. It explicitly requires that no store exists, so it cannot need ca_eccc to be ported and compiled. What it needs is ca_eccc declared a bulk provider so the surface routes it — configuration, not a compile.

Separating the declaration from the HYDAT compile would free RR5 from the spine. The declaration performs no irreversible act, so it would not even carry a safety edge. Not applied here: it needs the source read to confirm the declaration is genuinely separable.

The open decision: honour the Poland ordering, or override it?

The RR3 → RR4 edge is risk-ordering — soft by construction. Freeing RR5 alone changes nothing, because Poland simply becomes critical instead. But freeing RR5 and overriding this edge takes the critical path from five nodes to four.

Honour it and Poland runs after Canada, as the vision intends: a layout defect surfaces before Canada's stores are built on. Override it and they run together, roughly a fifth faster, at the cost of rebuilding Canada's stores if Poland falsifies the layout.

This is a cost-versus-rework judgement, not a technical one, and it belongs to the human. It is the first thing in this graph that is genuinely a fork rather than a fact — which is the argument for the graph carrying decisions as nodes with named owners, rather than leaving them to whoever reaches them first.

What deriving it changed

Three disagreements with the existing decomposition

The bulk surface moves after Canada, not before it

The milestone graph has m5 (bulk lifecycle) depending on m3, with m6 and m7 after it — the surface lands before the ports. But the criterion reads “call fetch for a ca_eccc station on a machine with no local store”. That cannot run until ca_eccc is a bulk provider. Taking the criterion literally reverses the order.

Receipts is not independent after all

The vision suggests the rename may run in parallel with the store work. Its criterion says the ca_eccc entry must be marked store_excerpt and carry the store path, the executed query, the format version and the source vintage — all of which are produced by the reader. The code change is independent; its falsifier is not. Real buildability edge on RR1.

“Two unlike sources read through one path” splits in half

Its one-path claim — no provider-specific branch on the read path — is testable immediately against two fixture stores of different shapes. Only its two-real-sources half needs both ports. Treating it as a single late criterion, which the milestone decomposition does, defers a check that would catch a provider branch at the very first package.

Poland needed a second safety edge, and its absence was dangerous

The first version of this graph gave RR4 one dependency: RR3, by risk-ordering. But Poland’s compile deletes its publisher artifacts under the same ADR 0021 rule as Canada’s, so it needs the certification harness for exactly the same reason.

Because risk-ordering edges are designed to be overridable, overriding that one for throughput would have compiled Poland with nothing protecting it — destroying the only copy of a source’s observations. The RR2 → RR4 safety edge is now explicit.

The general rule: an edge may only be omitted as transitively implied when every alternative path to it is at least as binding. Ordinary transitive reduction is unsafe once edges have kinds. With a single edge kind this bug is not merely undetected — it is inexpressible.

None of these came out of the earlier pass, because the earlier pass sorted existing milestones into new boxes. They only appear when the criteria are the input — and the last one only appeared when the graph’s acceptance test was written.

What the check catches

Before any work is dispatched

RR5 fails the mechanical check.

“Insufficient disk refuses before downloading” is not an executable command. The vision’s own risk list already knew: it needs an injectable free-space probe or a controlled environment, and says to decide the mechanism while building the download step, not at the end.

So RR5 returns for one correction — declare the probe as part of its own scope, or restate the criterion against something observable. That is the predicate doing its job at authoring time, on the first real graph it has ever seen.

The other ten criteria pass unchanged. They were already written as input / observation pairs, and each becomes exactly one package’s completion test.

What this still does not test

Stated so it isn’t assumed

RivRetrieve is single-repository, so the cut exercises no multi-repo package, no per-repo worktree, and no cross-repo consumer-test rule. That Fog survives the migration.

And this graph was authored by hand. Whether a dispatched agent produces the same partition from the vision alone — including noticing that a criterion names ca_eccc and therefore reorders the surface — is the open question the skill will answer.

One discrepancy to fix in code. The committed test fixture has drifted from this graph: “Four value states survive compile” and “Native values are unchanged on disk” are assigned to RR1 there, but both begin “Compile a fixture…” and therefore need the certification harness. They belong to RR2, as the partition above shows. Worth correcting before the fixture becomes the reference everyone copies.
