# Project domain context

## Canonical terms

| Term | Meaning |
|---|---|
| Program | A durable GitHub-tracked container for one big idea that requires multiple independent visions. A program is program-level discovery, not a build decomposition into milestones or steps. |
| Map | The single GitHub issue that holds a program's destination, notes, Decisions so far, fog, and links to its effort tickets. It is the program's sole durable state. |
| Effort ticket | A GitHub issue representing one ambitious, contained, vision-sized question within a program. Each effort ticket gets its own grill, vision, and PCE delivery cycle. |
| Fog-of-war / fog | Program territory that is acknowledged but not yet specified sharply enough to become an effort ticket. `Fog` is the accepted short form. |
| Frontier | The currently actionable set of open effort tickets whose blocking dependencies are satisfied. The frontier excludes fog and blocked tickets. |
| Fog-graduation | The land-time process that turns newly understood fog into seeded effort tickets and wires their blocking relationships without decomposing implementation work. |
| Chart | Survey a program breadth-first, create or refresh its map, mint only the effort tickets that are currently sharp, and leave unresolved territory in fog. Charting resolves no ticket. |
| Work | Claim one effort ticket, reconstruct its map and glossary context, grill it deeply toward one vision, and hand the result to vision creation. Working does not automatically run delivery. |
| Land | Prove from the binary-owned landing result that the linked vision was delivered and merged, collect the human's command and observation for every unpaid criterion, confirm the destination, close the effort ticket, add its one-line decision to the map, record and mint any negative destination divergence as named Effort work, graduate newly visible fog, and detect completion when the active map has no open linked effort tickets and no substantive fog. An unanswered unpaid observation blocks every GitHub mutation; a negative destination answer does not block effort-ticket closure. Map closure still requires separate confirmation. |
| Chart/work/land lifecycle | The program-level lifecycle in which charting establishes the visible map, working sharpens one effort ticket into a vision, and landing records the result and reveals the next frontier. |
| Decisions-so-far index | The concise section of the map that carries settled outcomes across effort tickets; an entry links an ADR when durable architectural rationale was recorded. It is an index, not a substitute for ADR detail. |
| Grill-with-docs | A one-question-at-a-time discovery process that combines deep interviewing with active maintenance of committed domain context and, only when warranted, ADRs. |
| Role frame | The versioned agent-facing scaffold the `pce` binary composes for one dispatch role, carrying ground-truth ref, read commands, environment hazards, output path, boundaries, and the role's fixed review obligations. The orchestrator supplies only the task-specific text. |
| Event log | The single ordered append-only file recording what only the orchestrator knows: one record per dispatch, deltas, escalations, key findings, measured repo contracts, and the identity of each approved planning artifact. Every record shares a fixed envelope — sequence, timestamp, kind, node, payload — over an open kind set whose payloads are validated per kind. Only the orchestrator appends; a record is written once, when the event occurs, and never revised. |
| Derived state | Run status computed on read rather than stored: whether a step merged, whether a branch or worktree exists, where a tag points, which node the run resumes at, how many rounds an artifact has spent, and which ref a dispatch was issued against. It is a fold over the three authorities named by the placement rule. Merge status is three-valued — merged, not merged, or inconclusive when the authorities disagree or one is unreachable — and inconclusive is never collapsed into either side. |
| Placement rule | The rule assigning every fact to its authority: git, `gh`, and the event log's own record sequence. A fact any authority implies is never also stored, so no running tally exists anywhere; a fact no authority implies is appended once, when it happens. |
| Run snapshot | The named, versioned JSON document the status verb emits: derived state, each repository's observation ref and fetch time, and a bounded recovery digest that names whatever it elided rather than truncating silently. It is the contract its consumers read; a human rendering is a separate view of the same computation. |
| Evidence command | The exact command or invocation that produced a claim, required on every event-log record asserting a fact about code, environment, or repository state. A fact-asserting record without one is rejected; a record that only reports an event carries none. |
| Labelled assertion | A factual claim the orchestrator inlines into a dispatch, admissible only when the receiving agent could not derive it at the ref, and only carrying the exact command that produced it. Every gate treats labelled assertions as its first verification target. |
| Decision hold | A keyed, idempotent escalation that blocks its dependent work and closes only when the human's answer is recorded and every dependent node is named and unblocked. |
| Convergence signal | The computed continuation test for a gate loop: blocker count strictly decreasing with no recurring finding. It replaces the round count as the escalation trigger; the round ceiling remains only as a cost backstop. |
| Enforcement split | The rule assigning each workflow invariant to a layer by its kind: prohibitions are command shapes enforced by hooks, verifications are computations owned by the `pce` binary, durable per-repo facts live in a tracked file read only from the default branch, and context the orchestrator must hold but cannot be relied on to fetch is injected at the harness boundary by a hook that fails open. |
| Landing confirmation | The single question landing asks the human: here is the delivered world in the same plain words you reacted to before it was built — is this where you wanted to land? Delivery itself is proved by the machine from the run's executed criteria, the merge state, and the event log, so nothing about mechanics is put to the human. A negative answer does not block the landing, because the work already merged and withholding closure unmerges nothing; it records the divergence and mints it as named work. |
| Unpaid criterion | An acceptance criterion that cannot be executed inside the run that delivers it, because what it tests lives outside the run's reach — a hook activated only by a human install, a promoted binary, a live environment measurement. The run reports done while naming each one, and landing collects them: the human states the command they ran and what they observed before the ticket closes. For the same acceptance criterion and finished result, an unpaid observation cannot replace a current failed status; only a later passed execution can advance that failure. Naming beats both alternatives, since halting a finished run on work only the human can do is a stop with no action available inside it, and silence is how a green report gets built on checks that never ran. |
| Planning descent | The move from intent to mechanism, performed by the actor that reads the code at the ref. The orchestrator hands down what must become true; the descending actor returns the structure only reading the source can establish. A level that has not read the code authors none of it. Graph nodes return genuine ordering alone; a write-set is authored solely in the plan, where the executor consumes it. |
| Reading depth | How far into the source a level descends, set by the claim it is making rather than by a rule assigned to the level. An actor reads exactly deep enough to sustain the ordering edge it asserts, and its critic checks that fact at the depth it was cited, so neither can hold information the other was denied. The orchestrator makes no such claim and so reads no code. |
| Concurrency admission | The rule deciding whether two ready nodes dispatch together, applied identically to steps and to milestones. It is a recovery path, not a prediction: overlap dispatches and the merge absorbs the rebase, because a rule that must predict safety has to be conservative, and a conservative rule never fires on real code. |
| Dispatchable set | The set of graph nodes the `pce` binary computes as startable now: a fold over ordering edges and three-valued merge status. Every node in it dispatches concurrently. A node whose dependency is inconclusive is reported as its own case rather than collapsed into ready or waiting, which is the collapse an orchestrator folding the graph in context makes. |
| Ordering edge | A `depends_on` entry in a graph artifact, admissible only when it names the code fact that makes the dependent node unbuildable until the other has merged. The default is no edge, and a shared file is never a reason, because overlap dispatches and the merge absorbs the rebase. A critic that reads the source and cannot sustain the stated reason deletes the edge; an unjustified edge is a defect exactly as a missing one is. |
| Vacuity | A check that passes for a reason unrelated to what it claims to test, most often because its own setup already guarantees the outcome. Reading cannot detect it, because the check's text is correct in every instance; only mutating the subject and observing the check stay green exposes it. |
| Marginal detection | The evidence a gate's retirement requires: against a versioned mutation corpus for the gate's claimed subject, every mutant the candidate gate catches is also caught by the remaining gate set once the candidate is removed. Surviving mutants measure whether a gate's own protection is non-vacuous, not whether it is redundant, so zero survivors is consistent with a gate being both effective and necessary and is never grounds to retire it. Hit rate is disqualified as a retirement measure. An incomplete mutation budget yields `inconclusive`, which is not evidence for permanent retention. |
| Milestone tier | An integration and promotion boundary, not a second decomposition tier. Its function is to gate the exact cumulative merge result before promoting it, which is the only level at which independently green steps are proven to compose. Independently green steps do not necessarily compose: a run measured a conflict that neither step could observe alone because each was green in its own worktree. Re-gating the integration branch before merging the next step does not test that step's composition, and gating a synthetic post-merge result recreates this tier's essential function under another name. |
| Liveness escalation threshold | The bound a run places on repeated non-production, expressed as dispatch liveness rather than as a cost ceiling. After two consecutive binary-owned non-production completions for the same node, role, and required artifact, an atomic admission check forbids a third issuance and records a typed non-production hold. A typed retry close resets the streak and opens a fresh two-attempt window; re-plan and abandon close the hold without reopening that key. Validated observed-child completions are productive and charge one defect round; an unstructured observed-child completion with its required artifact present and a reconciled-dead Produced completion are productive without charging a defect round. Production resets the streak. NotValidated with the required artifact absent, every Missing, Truncated, SchemaInvalid, or SchemaViolating completion, and reconciled-dead NotProduced are non-production. Presence-less legacy completions and unresolved issuances are neutral. Free-text escalation resolutions, delta records, and artifacts rescanned from disk never affect either counter. The issuance ordinal remains a separate exact count of every dispatch. This is not a proxy for subscription exhaustion: productive dispatches exhausting shared capacity remain a separate capacity problem, and setting a spend ceiling remains a non-goal. |
| Repository contract | What one repository durably says about itself to PCE, tracked in that repository and honoured only as it stands on the default branch, so no branch can relax its own gate. A repository with no contract gets one written for it and the run continues; nothing waits on a human, because a contract that does not yet exist has no gate to relax. It has two halves under different authorities. Its stated half — gate commands, version policy, and the workflow map — is a claim PCE falsifies by execution at base and that no run may edit. Its appendable half — environment hazards, gate orderings, lockfile rules — is inert text that no measurement can check, that PCE propagates verbatim into dispatches, and that a run may add to when a fact recurs. Conflating the halves is the failure mode: a run editing a gate command can weaken it below detection, while an unverified hazard note costs only tokens. |
| Stated half | The part of the repository contract that execution checks: gate commands, version policy, and the workflow map. A gate command counts as an acceptance gate only after PCE has run it at base and observed its exit status; a command that fails at base is not a gate. It is authored once, when no contract exists, from the repository's CI where CI exists and otherwise from the widest candidate command that passes at base — never from prose an agent reads and generalizes. Thereafter no run may edit it, because the base measurement catches a command that fails and cannot catch one that passes while testing nothing. Correcting it is an ordinary tracked-file edit read by the next run, not an event in any run. |
| Appendable half | The part of the repository contract that carries facts no execution can falsify. A run may append one when the same fact has recurred across runs in that repository, evidenced by its `key-finding` records. Nothing verifies an entry, and nothing needs to: a wrong entry costs prompt tokens rather than correctness, and requiring a human to admit each one would interrupt on session noise indistinguishable from a durable fact at discovery time. Every entry is a standing instruction that holds indefinitely, which excludes a doc-truth defect: that is true only until the document is corrected, so filing one guarantees the section rots. |
| Doc-truth defect | A statement committed in a repository that is false about that repository — a release guide describing a step two shipped releases skipped, a lockfile pinning a version its manifest contradicts, guidance instructing a cold agent to maintain state a landed ADR abolished. It matters because dispatched agents have no memory and read the repository to orient, so a false document produces confident wrong work rather than an error. It is a defect that becomes a fix, never a contract entry. |
| Workflow map | The stated half's account of continuous integration: every workflow present in the repository paired with either the local command that stands in for it or an explicit statement that none does. The repository supplies each pairing, since equivalence is a judgement only it can make; PCE enumerates the workflow directory itself and rejects a contract that omits a workflow that exists, since the observed failure was an omission and the omitting party cannot be asked whether it omitted anything. |
| Installed surface | The three things `install.sh` links into the live environment, treated as one unit: the `pce` binary, the skill directories, and the hooks. They are one unit because a single run reads all three and they can contradict each other — prose instructing a flag the binary rejects, or a hook denying a command the binary still requires — so they are promoted together or not at all. Two of the three are symlinks into the working tree rather than into build output, so a `git checkout` in the primary repository changes them for every run with no merge and no build step. |
| Promotion | The human act of making a dev installed surface operational. It is deliberate rather than automatic because the surface is shared across runs: a merged change is not yet a released one, which is the same human-only boundary that already governs tags and releases. |
| Surface pin | A run's recorded and verifiable binding to one installed surface, held for the life of that run. Recording alone is insufficient: a pin the run cannot check is vacuity applied to its own foundation, because the recorded intent and the executing artifact can diverge silently — an unmerged build once populated the shared binary and broke an unrelated concurrent run, and nothing inside that run could have reported it. Pinning per run rather than freezing one surface globally keeps one repository's releases off another repository's schedule. |
| Dispatch envelope | Everything about an invocation except its task text: the argument vector, the child's environment, its sandbox, working directory, standard-input binding, schema path and output path. The binary composes it and spawns the child directly, so no shell ever sees it. Invariants that were remembered become unspellable-otherwise: standard input is bound on the child handle rather than redirected, so the hang a missing `< /dev/null` causes is unreachable, and `ANTHROPIC_API_KEY` is stripped from every gate spawn, so a gate cannot silently bill an API account instead of the subscription. |
| Dispatch process identity | The binary-owned schema-version-1 sidecar fact recorded immediately after a logged dispatch spawn: its issuance sequence, the child's positive operating-system process number and Darwin start time, the absolute required artifact path, and, for newly authored sidecars, the owning continuation's inseparable process number and start identity. Pre-upgrade sidecars omit the optional continuation identity and remain readable and governed by the child-identity guard. Its filename is derived from the event-log path and issuance sequence, but it is not an event-log record. |
| Completion record | The second and final lifecycle record for a dispatch. Its observed-child outcome carries only binary-measured wall-clock duration, token usage, exit status, and artifact validation outcome. Its reconciled-dead outcome carries current artifact production and no duration, usage, exit status, or artifact-validation result. A record is never revised and either outcome occupies the same single completion slot. |
| Unaccounted dispatch ledger | The issuance-ordered set of dispatch issuances that have neither an observed-child nor a reconciled-dead completion. Every unmatched issuance remains enumerated across reads; the all-accounted statement is derived only when this ledger is empty. |
| Reconciled-dead completion | A durable dispatch-completion outcome conditionally appended after the child identity is dead, any recorded owning continuation identity is dead, and the whole event log is trustworthy. It records current artifact production without synthesizing child measurements. |
| Per-dispatch cost | Wall-clock duration and typed token usage for one dispatch, carried on its completion record. Dollars are deliberately excluded: `claude -p` computes `total_cost_usd` locally at list rates and that figure is not billing-authoritative on a subscription, while Codex reports no monetary figure at all, so a stored amount would mean nothing for either half and would invite comparison against an invoice it cannot reconcile. Availability is a tagged variant rather than a bare number, so a dispatch whose usage was not measured reports absence with a reason and never a zero that reads as a measurement. |
| Verdict artifact | The file a gate writes, and the only channel by which its result reaches the orchestrator. A missing or non-conforming artifact means the dispatch produced nothing; the child's transcript is never read as a fallback, because a backstop admissible once is admissible always and the invariant reverts to prose. Validation is post-hoc for gates, which have no `--output-schema` equivalent, and structural for Codex, which is given one. |
| Intent altitude | The only level at which the workflow addresses the human: what is being built, where it is going, whether that is still where they want to end up. Mechanism is never surfaced unless asked for, and detail is layered beneath the sentence that carries the intuition. A question the human cannot answer from taste is a defect in the question rather than a gap in the human, because the human supplies ideas and taste while the machine supplies technique. |
| Laundered decision | An approval the human could not evaluate, which lets the machine record its own choice as a human ruling. Observed twice: a byte-level reconciliation approved because no other response was available, and a threshold reverse-engineered from a figure wrong by 7.6x, attributed to an owner never asked, and nearly ratified. It is why a human is asked to confirm only what a human can confirm — the machine proves mechanics, the human confirms the destination. |
| Falsification gate | A gate that establishes a claim by trying to break the delivered artifact rather than by reading a description of it: mutating the subject and watching the check stay green, planting the violation a rule claims to prevent, deleting the rule's own configuration, feeding a deliberately invalid input and requiring refusal. It exists because the escaping defect class is green rather than red — a rubber stamp, an inert rule, an unreachable success outcome and a baseline wrong by 7.644x each passed every reading gate aimed at them. |
| Gate execution evidence | A harness-authored immutable record of one falsification stimulus: its exact shell-free command, input bytes, complete explicit environment, ordered setup, and observed process result. The gate supplies the stimulus and may cite the returned execution reference, but it neither supplies the observation nor writes the record; expected outcomes and replay interpretation are separate harness concerns. |
| Repair-sensitive replay | Two executions of the same harness-recorded stimulus at each of a named broken and repaired ref, each in a fresh materialized tree with no repository metadata and scheduled so invocation position does not identify either side, then compared for raw reproducibility before a harness-owned expected verdict outcome classifies relevance. Repository-root rebasing is relocation, not permission to alter any other stimulus byte. Parent-only configuration crosses a sanitized process boundary before replay, so it is absent from the stimulus's process ancestry. |
| Falsifier independence | The property that makes a check worth running: it binds to something the implementer does not control — the external system's own golden output, an enum extracted at the pinned ref, a captured real response. A suite authored beside its subject proves only their mutual consistency, measured as 39 tests and 37 named rejections agreeing perfectly about a data format the real system never emits. Independence comes from the anchor, never from the headcount of authors. |
| Reversibility dial | The rule setting how much pre-proof a unit of work receives, by whether its act can be repeated. Pre-proof earns its cost only where it cannot: minting an immutable artifact, publishing a release or tag, consuming a one-shot quota, destroying history. Everything else in a run is a revert or a re-plan, and gets a light brief and heavy falsification of what was built. |
| End-state picture | The plain-language account of what is true today and what is true after a vision lands, including what disappears, written so the human can recognise their own world in it. It exists because a human cannot enumerate their tacit assumptions on request but reacts instantly to a concrete description that violates one — the belief that legacy code is the documentation for porting surfaced only when six thousand deleted lines were mentioned in passing. Read again at landing, it is what the human confirms. |
| Carried context | What one piece of work learns, propagated into the next without anyone remembering to carry it. The cheapest measured quality lever in the corpus: a 51-file change took two plan rounds against a 4-file change's five, and a step approved at round 1 after a sibling's paid-for lessons were injected into its brief. Distinguished from the appendable half, which admits only facts recurring across runs. |
| Domain-modeling | The active discipline of maintaining canonical terms, aliases-to-avoid, relationships, and ambiguities in committed `CONTEXT.md`, plus recording consequential durable decisions sparingly in `docs/adr/`. |

## Aliases to avoid

| Avoid | Use instead | Why |
|---|---|---|
| Roadmap | Map | A roadmap implies a predetermined sequence; the map preserves fog-of-war and only charts what is currently knowable. |
| Task | Effort ticket | An effort ticket is a vision-sized question, not an implementation task or planner-authored step. |
| Backlog | Fog or frontier | Unspecified territory and actionable tickets have different states and must not be collapsed into one queue. |
| Build plan | Program or map | The program layer chooses vision-sized efforts; milestones and steps belong to the downstream delivery planner. |
| State file | Event log | A run's durable file records events that already happened; current status is derived from git and `gh`, so calling the file "state" invites storing a claim that can contradict ground truth. |
| Resume instructions | Run snapshot | A written next-action narrative is a maintained claim sitting beside the facts that already imply it; the snapshot computes the resume point from the authorities instead. |
| Round counter | Dispatch records | A maintained tally drifts from the artifacts it summarizes, which is the observed failure; a round count is the number of dispatch records for that artifact. |
| Prompt template | Role frame | A template is copied by hand and drifts per dispatch; a frame is composed by the binary and cannot be omitted. |
| Orientation sweep | Repository contract | The sweep names an agent inferring a repository's facts per run, which is how an acceptance gate that fails at base got invented and how a deleted `AGENTS.md` clause left seven workflow clauses stranded; a repository states its own facts and PCE measures them. |
| Sign-off | Confirmation at intent altitude | A sign-off is a signature on whatever was put in front of the human; confirmation names what they are competent to judge, which is the destination and never the mechanics. |
| Requirements gathering | Grill-with-docs | Gathering treats the human as a store of specifications to be extracted; the grill exists so the human understands what is being built well enough for their taste to bite, and the criteria are evidence that understanding happened. |
| Delivery-trust boundary | Landing confirmation | The assertion the boundary protected is now computed from the run's own executed criteria and the merge state, so trusting it is no longer a constraint but a refusal to look; what remains for the human is the one thing no computation supplies, which is whether the delivered world is the intended one. |
| Test coverage | Falsification gate | Coverage counts checks that ran; every green defect in the corpus was covered. What matters is whether a check can fail when its subject is broken. |
| Disjoint write-set rule | Concurrency admission | Naming the rule after its current predicate freezes the predicate; the question is what admits concurrent dispatch, and the disjointness test is one answer that never fired. |

## Relationships

| Concepts | Relationship |
|---|---|
| Program and map | A program has exactly one open map, and the map is the durable index for all program state. |
| Map and effort ticket | The map links every effort ticket; each effort ticket points back to its program map with exactly one root-level `Program: #N` line and, after Work, carries exactly one root-level `Vision: planning/<YYYY-MM-DD>-<slug>` line required by Land. |
| Fog and effort ticket | Fog remains only on the map until fog-graduation can state a contained, seeded effort ticket. |
| Effort ticket and frontier | An open effort ticket joins the frontier only when its blocking dependencies are satisfied. Blocking is represented natively: the `addBlockedBy` GraphQL mutation creates the edge and `Issue.blockedBy` / `Issue.blocking` query it, verified on `gh` 2.89.0. The `Depends on: #M` body line remains the contingency for a failed native write. |
| Chart, work, and land | Chart creates the visible program surface, work turns one effort ticket into one vision, and land records delivery before exposing more work. |
| Decisions-so-far index and ADR | The index carries a one-line cross-ticket outcome; an ADR supplies durable rationale only when the decision crosses the ADR threshold. |
| Grill-with-docs and domain-modeling | Grill-with-docs uses domain-modeling throughout discovery so established vocabulary and durable decisions survive into cold sessions. |
| Program layer and PCE delivery | The program layer selects independent visions; each vision is delivered separately by PCE, whose milestone and step decomposition remains program-blind. |
| Event log and derived state | Together they replace a single rewritten state file: the log carries what no authority implies, derivation answers everything git, `gh`, or the log's own sequence can, and no fact is written in two places. |
| Run snapshot and the rehydration hook | The hook injects the snapshot's recovery digest after compaction and on a resumed or compacted session start, never on a cold start; it selects the run by most recent log record and injects nothing when that choice is ambiguous. |
| Event log and the per-repo contract | A measured contract is appended as a record because no authority implies it; the tracked per-repo file later changes the contract's source, not its home. |
| Evidence command and labelled assertion | Every labelled assertion is a fact-asserting record and so already carries its evidence command; what distinguishes it is additionally passing the admission test for entering a dispatch. |
| Role frame and the skill | The binary owns the frame, the skill owns the task; agent-facing obligations live in the frame so they cannot be dropped, and the skill keeps only orchestration logic. |
| Labelled assertion and the ref | The ref is the only authority and no actor's assertion is transitive, so an assertion is admissible only when it cannot be re-derived at the ref. |
| Convergence signal and decision hold | The signal decides when a loop stops; the hold defines what an unresolved stop owes the human before it can close. |
| Convergence signal and critique completeness | A gate loop layers — the fix introducing the next round's finding — only where the critic leaves the fix to the author's invention. Measured at one of six loops in the planning-descent run, and absent from every loop whose `required_change` supplied the replacement verbatim. Layering is a property of how completely a critique specifies its fix, not of adversarial review itself. |
| Landing confirmation and the end-state picture | Landing confirmation is composed only from the linked vision's `Goal / Why` and `Scope — In`, restated together in plain language. It asks whether that delivered world is the intended one after binary-owned delivery proof and required unpaid observations, so the human judges the destination rather than mechanics. A negative answer becomes named Effort work and does not block the selected ticket from closing. |
| Planning descent and concurrency admission | The descent produces the structure admission consumes; a write-set authored by a level that read no code cannot support any scheduling decision, whichever rule reads it. |
| Dispatchable set and the placement rule | The graph is not a fourth authority. The event log already names each approved planning artifact by path and SHA-256, so the computation reads the artifact the log identifies and the three authorities stay as ADR 0002 fixed them. |
| Step descent and the milestone graph | A step graph refines one milestone node and may not contradict it silently. The step planner is the first actor reading deep enough to falsify a milestone edge, so a refuted one routes upward as `root_cause: milestone_plan`. It licenses deleting that edge, never re-cutting what the milestones are. |
| Dispatchable set and ordering edge | The set is the only mechanized consumer the graph has once write-sets leave it; without it, a justified edge is read solely by an actor under context pressure and the descent buys nothing enforceable. |
| Ordering edge and version policy | A repository's version-bump policy never becomes an edge. It reaches the dispatchable-set computation as a live per-invocation input, so a critic can refute any edge knowing nothing but the code, and a policy that changed between runs cannot leave a stale chain on disk. |
| Ordering edge and concurrency admission | Admission no longer restrains dispatch, so the edge is the only thing left that can make one node wait for another; that sole responsibility is why the edge, and not its absence, carries the burden of proof. |
| Repository contract and the event log | The contract still lands as a `repository-contract` record, so the tracked file changes the contract's source rather than its home: the orchestrator reads the file at default-branch HEAD and appends what it read and measured, instead of appending what an agent inferred. |
| Appendable half and the key-finding record | A fact learned mid-run stays where the run already puts facts — a `key-finding` record carrying the command that produced it — and the run keeps using it. Recurrence across runs is what admits it to the file, which makes the promotion test a computation over records rather than a judgement made at discovery time, when nothing distinguishes a durable repository fact from session noise. |
| Stated half and vacuity | Falsification at base is asymmetric: it detects a command that fails at base and therefore never was a gate, and it cannot detect a command that passes at base while testing nothing. That asymmetry, not distrust of any actor, is why the stated half is immutable to runs. |
| Repository contract and continuous integration | CI is the stated half's source wherever it exists, because a repository's workflows already encode what it treats as acceptance — that is a fact PCE reads rather than a judgement it makes. Where no CI exists, the widest candidate command that passes at base is taken instead of the first one found. |
| Freshness and the consumer's test command | There is no separate freshness command to configure. A consumer's freshness is its own `test` command from its stated half, because a field that can be filled in per run can be filled in wrong, and one filled with a compile-only check stayed green over twenty-one failing tests and dispatched work onto a broken base. A red result is compared against the pre-merge base before it is attributed, so a pre-existing failure is never reported as a regression caused by the producer's merge. |
| Installed surface and the PCE-modifies-PCE constraint | The ordering constraint reasons only about the run doing the modifying: a mid-run skill change is inert because the skill loads once, while a merged CLI change reaches later dispatches of that same run. It is silent about other runs, which read the same links. The surface is a cross-run channel, so a run that changes it can break a run that never touched its repository. |
| Surface pin and vacuity | A pin that only records what a run intended to bind is unfalsifiable in exactly the way a check whose own setup guarantees its outcome is: both report success without ever making contact with the thing they claim about. The surface must be able to state its own identity before a pin is a claim rather than a note. |
| Vacuity and evidence command | An evidence command records how a claim was produced; vacuity is the failure that survives it, because the command ran and reported success for a reason unrelated to the claim. Provenance and falsifiability are separate obligations. |
| Dispatch envelope and role frame | The envelope is the invocation's shape and the frame is its text; the binary owns both, and neither the orchestrator nor a shell composes either. Splitting them this way keeps the mechanical invariants independent of what any role is asked to do, so a new role inherits closed stdin, stripped credentials and a validated output path without restating them. |
| Dispatch process identity and dispatch liveness | The sidecar binds one issuance sequence and required artifact to a process number plus Darwin start identity; a later liveness observation must re-query and match the complete operating-system identity, because a matching reused process number alone is not the dispatched child. |
| Stated half and the enforcing environment | A gate is measured in the environment that enforces it. A command measured on the host and enforced inside the executor's sandbox certifies a machine that is not the one running it, which is how a command that fails for every executor entered two repositories' contracts as an acceptance gate. Measured where it is enforced, such a command fails at base and the existing rule disposes of it: a command that fails at base is not a gate. No verdict vocabulary is needed for a fault that never reaches an executor. |
| Environment fault and the binary's own measurements | A sandbox that degrades mid-run is established by re-running the gate in the identical shape and comparing the result to the base measurement, not by an executor asserting something about its own environment. Green at base and red now, both observed by the binary in the enforcing environment, is a computation, which is where the enforcement split already puts verifications. |
| End-state picture and acceptance criteria | Two forms of one content. The picture is what the human reads and reacts to; the criteria are the same claims written so a machine can execute them. A criterion names an input and an observation, never a test that must exist — "must be tested" is satisfied by a test existing, which is how thirty-nine passing tests guarded nothing. |
| Falsification gate and its mandate | A gate that executes trips over breakage nobody claimed, so its limit is the form of its evidence rather than the topic it stays on: it may block on any break it can demonstrate, naming the input it fed and what it observed, and may never block on a reading-based opinion however well argued. A scope fence would have filed the rubber stamp, the inert lint rule, and the baseline wrong by 7.644x as notes, since none was what its finder was looking for. The evidence bar is also the harder termination condition, because a gate can only speak where it holds a demonstration. |
| Falsification gate, verdict artifact, and gate execution evidence | The gate submits stimuli and writes its verdict; the parent dispatch executes and records every submitted stimulus, then admits a blocking issue only when that issue and its replacement each cite records from the same dispatch. A citation proves provenance, not relevance: repair-sensitive replay supplies that later interpretation. |
| Gate execution evidence, repair-sensitive replay, and a later campaign | Gate execution evidence supplies the stimulus and provenance, while repair-sensitive replay establishes direction for a replayable recorded execution; direction alone does not prove that the stimulus exercised the claimed behavior. For the paired execution case, the later campaign admits a broken finding and repaired approval only when independently recorded instances of the same binary-owned ordinary-gate probe run within their repository, name repository-relative program and inputs, survive root-only relocation, and are both repair-sensitive. |
| Falsification gate and critique completeness | A gate that executed its finding already holds the replacement, so handing over prose forces the author to reinvent it — the one measured cause of layering. The critic hands over what it ran; the author applies it; the next round verifies application rather than re-litigating the finding. |
| Reversibility dial and the plan | Where an act repeats, the plan keeps only its scope fence and its exact expected values, both of which the corpus proved load-bearing, and the pre-derived correctness argument moves onto the built artifact. Where it cannot repeat, pre-proof is the only proof available, because there is no second attempt to learn from. |
| Intent altitude and deviation | Plans bend on contact with reality and the human does not want live narration of a run in flight. What the altitude requires is that a bend reaches them as a bend — stated in their own terms, unprompted — rather than as a silently different destination discovered at the end. |
| Ratified criteria and their growth | The criteria settled in the grill are a floor a run may raise and never lower. A run may add a blocking criterion when reality produces one, and every addition reaches the human as a change of course rather than surfacing in the final report; nothing may remove or weaken a ratified one. Freezing the list would not prevent new requirements, only hide them, while additions-only means the definition of done can never quietly get easier. |
| Acceptance criteria and the run's own done | A run executes the vision's criteria against the finished thing before it may report done, and reports each as the input it fed and what it observed. Per-piece falsification cannot cover a criterion spanning several milestones, which is the one that fails silently: milestone 8 passed every gate aimed at its parts while the delivered whole was a rubber stamp. A criterion not executable inside the run that delivers it is named as such rather than reported green. |
| Completion record and round derivation | The issuance ordinal advances from every dispatch record. A defect round advances only from a current observed-child completion whose artifact outcome is Validated. Consecutive non-production is keyed by the issuance's sidecar-observed required-artifact identity and changes only from a current observed-child presence fact, reconciled-dead production fact, or typed retry close; a legacy presence-less completion and an unresolved issuance are neutral. |
